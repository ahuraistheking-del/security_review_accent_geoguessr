How the Vulnerabilities Were Found


The Starting Point
The starting point was the public repository github.com/quentinrauschenbach/accent_geoguessr. First the README was read to understand what the application does and how it is operated. It became clear that this is a classroom game for English lessons, that two roles exist, a teacher and students, and that the application runs on Streamlit and is publicly reachable. The last point mattered most, because an application that only runs in a local classroom would be judged by entirely different standards than one exposed to the open internet.

The Overview of the Files
Before actually reading the code, the file structure of the repository was surveyed. The main folder contained the two Python files app.py and app_local.py, the dependencies in requirements.txt, the README.md, the configuration in .gitignore, and a clips folder with a .gitkeep file for empty directories. The .DS_Store file in the root directory was noticeable, a system file generated by macOS that had been uploaded unintentionally. Such files normally contain no sensitive data but signal careless cleanup when publishing, and were therefore noted. The clips folder together with the commit message Upload MP3s also showed that file uploads are actually planned, which the review of the upload section in the code confirmed. The commit messages of the recent weeks additionally revealed that the project is under active development, so the reviewed state could still change.

The Look into the Source Code
Afterwards all files in the repository were reviewed. The main file app.py contained the complete application logic, the teacher view, the student view, the shared game state, and the scoring. The file was read top to bottom while watching for the usual suspicious spots: passwords, keys, file access, user input that gets processed further, and places where role decisions are made.

The first noticeable hit came right at the beginning of the file. While reading the first lines the line with TEACHER_PASSWORD stood out, because a password sat directly in the code. A quick look at the repository confirmed that it is public, so anyone who knows the repository name can read this line. In the same step it became apparent that the password consists of only four digits and looks like a date. The question of whether changing the file would get rid of the password led to a look into the commit history, and there the real problem appeared: old versions of the file remain permanently retrievable, so the password cannot simply be made to disappear.

The next observation came from reading the login section. The password comparison happens without any restriction, there was no counter for failed attempts, no delay, and no lockout. Together with the four digits it was immediately clear that a simple script would exhaust all ten thousand combinations faster than one can read the code. This insight was more a conclusion from what was read than a finding in the strict sense.

Further reading brought two spots to attention that had to do with the join URL. The QR code students scan was built from the Host header of the request. A look into the Streamlit documentation confirmed that this header is sent by the client and is therefore determined by the caller. The consequence was obvious: anyone who opens the page with a forged Host header changes the content of the QR code that then appears on the projector. The picture of students landing on a cloned page followed on its own.

The shared game state was the next section that deserved closer attention. It was visible that all data sits in a single dictionary shared via st.cache_resource, and that the student name is the only key under which guesses are stored. Three questions followed, answered by reading through the student section: what happens when two people pick the same name, what happens when the lock button is pressed again in a fresh session, and is there a deadline after which no more guesses are accepted? The answer to all three was sobering: names collide silently, the lock lives only in the browser session_state and disappears with every fresh tab, and no deadline existed, guesses were still scored after the reveal was already visible on the projector.

The role check was the last major section in the code. Access to the teacher view ran through the query parameter role=teacher and the password. While reading, the question became relevant whether the check happens again before every single teacher block or only on first load. The visible code did not answer that unambiguously, so the report described this point as presumably insufficient and marked it for own verification, rather than asserting something the code did not clearly support.

The upload section was another area that received close attention. It showed that files landed in the clips folder without any visible validation of filename, size, or content type in the reviewed code. From this observation followed the known risks of path components in the filename, of storage exhaustion on the cloud platform, and of arbitrary file types on the server. Here too it was less a single finding than the absence of things one would have expected and that were not there.

The Follow Up Research with Tools
After manually reading the code, systematic follow up research followed to solidify the observations and fill gaps. Three kinds of tools were used that complemented each other.

First, a few self written small scripts, among others to send requests against the running instance and evaluate the server responses directly, checking headers, cookies, and redirect behavior in a structured way instead of verifying everything by hand in the browser.

Second, some pre built tools, meaning finished scripts and libraries with which such checks can be standardized. They mainly provided the classic configuration checks, such as which headers are set and which are missing, and helped ensure nothing was overlooked.

Third, several online tools with which a public website can be assessed from the outside. They evaluate among other things the security headers, cookie settings, and the identifiability of the server technology. These tools supplied the numeric scores and classifications in the report, for example regarding the Content Security Policy, HSTS, and the cross origin settings.

Important with all tools was the translation back into the own code and own observation: every automated finding was only included in the report when it could be verified against the source code or the server responses. This way false positives could be ruled out and platform side findings, such as the tracking cookie, could be separated from findings that concern the application itself.

The Look at the Running Website
In parallel to the follow up research, the actually running instance was visited, both areas, the normal student view and the teacher panel. The tool for this was the browser with the developer tools. The network tab showed the server responses, the application tab showed the cookies being set, and the response headers showed the security headers.

There the picture was mixed. On the good side stood correctly set session cookies with Secure, HttpOnly, and SameSite, no open CORS allowances, and a nosniff header on the main page. On the other side the Content Security Policy was missing, the protection against embedding in foreign frames, the Strict Transport Security header, and the Referrer Policy. The missing CSP was the most striking single finding, because it is the most important line of defense against injected scripts and its absence makes every other problem on the page weigh heavier.

An interesting moment was the comparison of the cookies. The Streamlit own cookies were cleanly set, but a cookie named proxy-tracking-id stood out because it was set without HttpOnly and without Secure. A short cross check showed that this cookie does not come from the application itself but from the platform infrastructure, and thus lies outside the project's control. Exactly this distinction, what the application itself controls and what the platform does, shaped the classification of all delivery layer findings afterwards.

The server side information also became visible from the connection data, Google Cloud, a content delivery network, and an Nginx with a recognizable version number. That was no targeted attack, it simply stood in the headers and connection data the browser provides.

Additionally it was observed what was not there. There were no open debug endpoints, no directory listings, no error messages with internal details, no passwords transmitted unencrypted, and no private keys in the responses. This negative observation was in the end just as valuable as the positive findings, because it shows that the application has none of the classic gross misconfigurations and that the real risks lie elsewhere, namely in the logic and configuration of the code.

What Can Be Learned from the Approach
Most of the findings did not come from sophisticated tools but from three simple habits. First, actually reading the source code line by line, especially the first hundred lines where configuration and passwords usually sit. Second, asking for every piece of user input who controls it and where it ends up, which led directly to the host header and the manipulable game state. Third, looking at the running application in the browser with developer tools while also taking the absence of things seriously, because missing headers are just as meaningful as existing errors.

The only point that remained open at the end was the question of whether the role check happens again before every teacher block. The code did not support an unambiguous answer, and the instance was shut down before this question could be settled by a test. It therefore stands in the report as a point for later verification, once the revised version is back online.
